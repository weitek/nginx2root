nginx2root exposure checker#

Безопасная внешняя проверка: подвержен ли сайт уязвимостям nginx2root, опубликованным Xint 18 ноября 2026 года и исправленным в nginx 1.31.9 и 1.30.7.

Инструмент делает только рукопожатие и обычные запросы. Он не эксплуатирует уязвимости: не отправляет WINDOW_UPDATE-флуд, не рвёт потоки через RST_STREAM и не пытается вызвать падение воркера.

Уязвимости#

CVE Что это Уязвимы Нужно для атаки
CVE-2026-123007переполнение окна flow control в HTTP/2 (RCE, critical)1.9.5–1.31.8HTTP/2
CVE-2026-123634use-after-free в resolver0.6.18–1.31.8resolver + proxy_pass с переменной + mirror
CVE-2026-123633use-after-free в HTTP/21.19.7–1.31.8HTTP/2 + проксирование на upstream
CVE-2026-121810use-after-free в HTTP/31.25.0–1.31.8HTTP/3 + проксирование на upstream
CVE-2026-113425use-after-free в mail proxy0.5.33–1.31.8proxy on + auth_http

Официальные источники: nginx security advisories, nginx CHANGES 1.31.9, разбор Xint.

Требования#

  • Python 3.8+ (проверено на 3.12), только стандартная библиотека.
  • Для --verify нужен системный набор CA-сертификатов.
  • Для интеграционных тестов — docker и openssl.

Использование#

./nginx2root_check.py https://example.com
./nginx2root_check.py example.com:8443 --timeout 8
./nginx2root_check.py https://example.com --json > report.json
./nginx2root_check.py --file targets.txt --concurrency 4
cat targets.txt | ./nginx2root_check.py --no-h3

Полезные флаги:

Флаг Смысл
--jsonмашиночитаемый отчёт (схема ниже)
--port Nпереопределить порт для всех целей
--path /xпуть для fingerprint-запроса

Коды выхода: 0 — проблем не найдено, 1 — есть LIKELY_VULNERABLE, 2 — результат неопределён (CDN, неизвестная версия, ошибка), 3 — ошибка аргументов.

Что именно проверяется#

  1. TLS/ALPN. Отдельное рукопожатие с ALPN=["h2","http/1.1"]. Если сервер согласовал h2, значит HTTP/2 включён на этом порту — это условие CVE-2026-123007 и CVE-2026-123633.
  2. HTTP/1.1 fingerprint. HEAD / и, если версия не видна, GET на несуществующий путь: Server:, тело дефолтной страницы ошибки, признак дистрибутивной сборки ((Ubuntu), (Debian)), заголовки CDN. OpenResty, Tengine, Angie, Kong и APISIX распознаются как nginx-семейство: они содержат ядро nginx и подвержены тем же CVE.
  3. HTTP/2-обмен. Preface + SETTINGS + один HEADERS (GET /). Подтверждает, что за ALPN действительно живой HTTP/2. Никаких управляющих кадров, влияющих на окна.
  4. HTTP/3. Заголовок Alt-Svc с h3 и UDP-проба QUIC: отправляется Initial с неподдерживаемой версией, сервер должен ответить Version Negotiation.
  5. Вердикты. Версия сверяется с диапазонами: 1.9.5–1.31.8 и 1.30.0–1.30.6 уязвимы; 1.31.9+ и 1.30.7+ исправлены; ≤1.9.4 не затронуты.

Как читать вывод#

Каждый CVE получает две вещи: verdict (метку) и действие — что делать.

Метка Код Действие
ВЕРОЯТНО УЯЗВИМLIKELY_VULNERABLEобновить nginx до 1.31.9/1.30.7
ИСПРАВЛЕНОPATCHEDничего не делать
ПУТЬ АТАКИ ЗАКРЫТMITIGATEDничего не делать (обновить при возможности)
НЕ ЗАТРОНУТNOT_AFFECTEDничего не делать
НЕ ПРИМЕНИМОNOT_APPLICABLE— (сервер не nginx)
НЕОПРЕДЕЛЁННОINCONCLUSIVEпроверить вручную: CDN/бэкпорт/ошибка связи
ПРОВЕРИТЬ НА СЕРВЕРЕUNKNOWNпроверить конфигурацию на хосте

Последняя строка отчёта — прямой ответ на вопрос «надо что-то делать?»:

ИТОГ Значение Код выхода
ТРЕБУЕТСЯ ДЕЙСТВИЕесть LIKELY_VULNERABLE1
НУЖНА РУЧНАЯ ПРОВЕРКАесть INCONCLUSIVE2
ДЕЙСТВИЙ НЕ ТРЕБУЕТСЯтолько PATCHED/MITIGATED/NOT_AFFECTED0
ПРОВЕРКА НЕ ВЫПОЛНЕНАнет DNS/соединения, CVE не проверялись2

Если проверка невозможна (DNS, таймаут, TLS), таблица CVE не выводится — вместо неё причина и рекомендация. При --no-h3 вердикт HTTP/3 становится ПРОВЕРИТЬ НА СЕРВЕРЕ и не влияет на код выхода. Если UDP/443 не ответил, HTTP/3 тоже помечается ПРОВЕРИТЬ НА СЕРВЕРЕ: молчание UDP может означать фильтр, а не отсутствие HTTP/3.

Таймауты и сетевые ошибки повторяются до --attempts раз (по умолчанию 3). Если ответ получен не с первой попытки, в note появляется строка «связь нестабильна: успешный ответ получен с попытки N из M».

Версия берётся не только из nginx/1.30.7, но и из вендорских токенов: nginx-reuseport/1.30.7, nginx-naxsi/1.24.0, nginx-extras/1.18.0. Для таких сборок добавляется note с исходным токеном.

Пример:

При ошибке DNS:

  ИТОГ: ПРОВЕРКА НЕ ВЫПОЛНЕНА — выводов об уязвимости сделать нельзя.

Ограничения#

  • Версия — не приговор. Ubuntu 22.04 (1.18.0-6ubuntu14.22), Debian, RHEL и другие дистрибутивы бэкпортируют исправления, не меняя nginx -v. Для таких сборок чекер выдаёт INCONCLUSIVE — сверяйтесь с USN-8955-1 и аналогичными advisory.
  • CDN. Если перед nginx стоит Cloudflare/Akamai/Fastly, проверка видит только edge. Чекер это распознаёт и выдаёт INCONCLUSIVE; для точного результата запускайте его против origin.
  • CVE-2026-123634 и CVE-2026-113425 определяются только конфигурацией. Снаружи их проверить нельзя — нужен доступ на хост.
  • Скрытая версия. При server_tokens off остаётся вывод «HTTP/2 включён, версия неизвестна»; это трактуется как риск, потому что исправленные релизы вышли только 18.11.2026. OpenResty и другие форки скрывают версию ядра nginx — их патч-статус проверяется на хосте (openresty -v).
  • Фильтрация по IP. Если TCP-порт открыт, но TLS-рукопожатие и HTTP-запрос молчат, это обычно geo/anti-DDoS-фильтрация вашей сети, а не проблема сайта: проверьте доступность с другой точки (SSL Labs, внешний fetch) и запустите чекер из разрешённой сети.
  • Проверка не является пентестом и не гарантирует отсутствие уязвимости.

Что сделать на хосте#

Подробная пошаговая инструкция под root (версия, модули, конфиг, ALPN, действия, признаки эксплуатации) — в docs/server-check.md.

Кратко:

nginx -v                       # 1.9.5..1.31.8 => код уязвим
nginx -V 2>&1 | grep -- --with-http_v2_module
sudo nginx -T | grep -nE 'listen[[:space:]].*http2|^[[:space:]]*http2[[:space:]]+on'

Обновление: nginx 1.31.9 или 1.30.7, затем перезапуск (reload не заменяет исполняемый файл). Временная мера для двух HTTP/2-CVE — http2 off; в затронутых server-блоках; для HTTP/3 — убрать quic-листeners и http3 off;; для mail proxy — закрыть IMAP/POP3/SMTP от недоверенных сетей.

Этика#

Проверяйте только свои серверы или хосты, на проверку которых у вас есть письменное разрешение. Чекер не выполняет атакующих действий, но сам факт сканирования может нарушать правила площадки или законодательство.

Проверка nginx на сервере: пошаговая инструкция#

Для случаев, когда снаружи проверить нельзя (CDN, anti-DDoS, закрытая сеть) или нужно подтвердить вердикт ПРОВЕРИТЬ НА СЕРВЕРЕ. Инструкция — для nginx (пакет или своя сборка), не для OpenResty. Все команды выполняются под root.

До раздела «Действия» ничего не меняется: только чтение и один дамп конфига.

0. Подготовка#

sudo -i
whoami

Ожидаем root. Если sudo нет — войдите root напрямую.

1. Версия nginx#

nginx -v
nginx -V 2>&1

Первая команда печатает строку вида nginx version: nginx/1.24.0. Вторая — версию плюс флаги сборки.

Полная версия пакета (для дистрибутивных сборок):

dpkg -l | grep -E '^ii\s+nginx' 2>/dev/null
rpm -q nginx 2>/dev/null

Проверьте, что запущен именно этот бинарник:

ps -eo pid,args | grep '[n]ginx'
ls -l /proc/$(cat /run/nginx.pid)/exe

Если путь в /proc/.../exe отличается от command -v nginx — nginx -v показывает не тот бинарник, который работает.

Как читать версию#

Версия Оценка
1.9.5 – 1.31.8код уязвим к CVE-2026-123007 (если включён HTTP/2)
1.30.0 – 1.30.6уязвима ветка 1.30
1.31.9+ или 1.30.7+исправлено
1.9.4 и старшене затронута HTTP/2-уязвимостями
nginx-reuseport/1.30.7, nginx-naxsi/1.24.0вендорский токен: ядро — цифры после / (здесь 1.30.7 и 1.24.0)
1.18.0-6ubuntu14.22 и подобныедистрибутивная сборка: nginx -v не показывает бэкпорт, сверяйте полную версию пакета с advisory (Ubuntu — USN-8955-1)

2. Модули#

nginx -V 2>&1 | tr ' ' '\n' | grep -E -- '--with-http_v2_module|--with-http_v3_module|--with-mail'
  • --with-http_v2_module — в бинарнике есть код HTTP/2 (уязвим, если не пропатчен);
  • --with-http_v3_module — есть HTTP/3;
  • --with-mail — есть mail proxy (для CVE-2026-113425).

Если http_v2_module отсутствует — CVE-2026-123007 и -123633 неприменимы.

3. Конфигурация#

Сначала проверка синтаксиса и дамп:

nginx -t
nginx -T > /root/nginx-config-$(date +%F).txt 2>&1
nginx -T читает конфиг с диска. Если конфиг правили без reload, работающая конфигурация может отличаться. Сравните время изменения файлов с временем старта master-процесса (ps -o lstart= -p $(cat /run/nginx.pid)).

Дальше ищите по дампу (FILE — имя созданного файла).

3.1. HTTP/2 (CVE-2026-123007, CVE-2026-123633)#

grep -nE 'listen[^;]*http2|^[[:space:]]*http2[[:space:]]+on' /root/nginx-config-*.txt
  • listen 443 ssl http2; — старый синтаксис (nginx ≤ 1.25.0);
  • http2 on; — новый (1.25.1+);
  • пусто — HTTP/2 не включён.

Проверьте все server-блоки на том же адресе и порту: протокол согласуется на listening socket, а не на отдельном location.

3.2. HTTP/3 (CVE-2026-121810)#

grep -nE 'listen[^;]*quic|^[[:space:]]*http3[[:space:]]+on|Alt-Svc' /root/nginx-config-*.txt
ss -lunp 'sport = :443'

Если ss показывает nginx на UDP/443 — QUIC-листener активен.

3.3. Resolver + переменный proxy_pass + mirror (CVE-2026-123634)#

grep -nE '^[[:space:]]*resolver[[:space:]]' /root/nginx-config-*.txt
grep -nE 'proxy_pass[[:space:]]+https?://[^;]*\$' /root/nginx-config-*.txt
grep -nE '^[[:space:]]*mirror[[:space:]]' /root/nginx-config-*.txt

Нужны все три условия: resolver, proxy_pass с переменной (DNS-резолв во время запроса) и mirror. mirror появился в 1.13.4; на более старых версиях путь через mirror невозможен, но advisory допускает другие subrequest-механизмы (например SSI).

3.4. Mail proxy (CVE-2026-113425)#

grep -nE '^[[:space:]]*mail[[:space:]]*\{|^[[:space:]]*proxy[[:space:]]+on|^[[:space:]]*auth_http[[:space:]]' /root/nginx-config-*.txt

Нужны mail, proxy on и auth_http одновременно. Для обычного веб-сервера этот CVE неприменим.

4. Фактический протокол на самом сервере#

Сначала узнайте, где слушает nginx:

ss -ltnp | grep nginx

Дальше проверьте ALPN на нужном адресе и порту (подставьте свой SNI и порт; для примера — 127.0.0.1:443):

openssl s_client -connect 127.0.0.1:443 -servername example.com -alpn h2,http/1.1 </dev/null 2>&1 \
  | grep -E 'ALPN protocol|No ALPN negotiated'
  • ALPN protocol: h2 — HTTP/2 реально работает;
  • No ALPN negotiated — HTTP/2 выключен.

Если nginx за локальным прокси слушает 127.0.0.1:8080, проверяйте этот порт (там может быть обычный HTTP без TLS).

Проверка запросом (если curl собран с HTTP/2 — видно в curl -V):

curl -V | head -1
curl -skI --http2 --resolve example.com:443:127.0.0.1 https://example.com/

Ошибка HTTP/2 not supported означает, что сервер не согласовал h2.

5. Проверка, не эксплуатировали ли уязвимость#

ss -tinp state established '( sport = :443 )'

Запустите дважды с интервалом и сравните bytes_received/bytes_sent. Подозрительно: один долгий коннект с быстро растущим входящим трафиком и много коротких TLS-соединений с того же IP.

grep -Ei 'worker process.*exited|signal 11|segfault' /var/log/nginx/error.log
coredumpctl list 2>/dev/null | grep nginx

Аномальные завершения воркеров — слабый, но полезный признак.

ps -eo uid,user,pid,ppid,args | grep '[n]ginx: worker'

Запомните UID воркера и включите аудит запуска процессов (если есть auditd):

auditctl -a always,exit -F arch=b64 -S execve,execveat -F euid=<UID> -k nginx_worker_exec
ausearch -k nginx_worker_exec -ts recent -i

Любой /bin/sh, /bin/bash или другой процесс, запущенный воркером nginx, — признак компрометации. Правило видит только события после установки.

6. Действия#

6.1. Обновление (основное)#

apt update && apt install --only-upgrade nginx     # Debian/Ubuntu
# или
dnf upgrade nginx                                   # RHEL-семейство
nginx -v
systemctl restart nginx

Нужна сборка с ядром 1.31.9+ или 1.30.7+ (либо дистрибутив с бэкпортом). reload не заменяет исполняемый файл — только restart.

6.2. Временная мера: выключить HTTP/2#

nginx 1.25.1 и новее — в каждом затронутом server:

listen 443 ssl;
http2 off;

nginx 1.9.5–1.25.0 — убрать параметр:

listen 443 ssl;

Затем:

nginx -t
systemctl reload nginx
ps -eo pid,args | grep 'worker process is shutting down'

Если старые воркеры остались — systemctl restart nginx (они держат уже открытые h2-соединения). После этого повторите проверку ALPN из раздела 4.

6.3. HTTP/3#

В затронутых server:

listen 443 ssl;
# listen 443 quic reuseport;
http3 off;
add_header Alt-Svc 'clear' always;
nginx -t && systemctl reload nginx
ss -lunp 'sport = :443'

В выводе не должно остаться nginx.

6.4. Resolver + mirror#

Уберите mirror или замените proxy_pass с переменной на фиксированный upstream:

upstream backend_fixed {
    server 10.0.0.10:8080;
}
location / {
    mirror off;
    proxy_pass http://backend_fixed;
}

mirror_request_body on; останавливает протестированный эксплойт, но не исправляет ошибку — не полагайтесь на него.

6.5. Mail proxy#

Если внешний доступ не нужен — слушать только loopback:

listen 127.0.0.1:143;

Иначе — ограничить порты 25/110/143/465/587/993/995 на firewall.

7. Чек-лист#

  • nginx -v и полная версия пакета записаны;
  • проверено, что запущен именно этот бинарник;
  • -V проверен на --with-http_v2_module;
  • nginx -T сохранён, h2/h3/resolver/mirror/mail проверены по дампу;
  • ALPN на loopback: h2 или http/1.1;
  • ss -lunp 'sport = :443' — есть ли QUIC;
  • просмотрены error.log и ss на предмет аномалий;
  • при необходимости выполнено обновление и restart;
  • после изменений повторно проверен ALPN и nginx -v.

Сохраните: вывод nginx -v, nginx -V, строки из -T по найденным директивам (без сертификатов и паролей), ss -ltnp, результат ALPN и nginx-config-*.txt в защищённом месте.

Если Server снаружи отвечает openresty, команды те же, но бинарник и сервис называются openresty, а версия ядра — первые три числа в openresty/1.25.3.2 (это 1.25.3).
