# nginx2root exposure checker

Безопасная внешняя проверка: подвержен ли сайт уязвимостям **nginx2root**,
опубликованным Xint 18 ноября 2026 года и исправленным в **nginx 1.31.9** и
**1.30.7**.

Инструмент делает только рукопожатие и обычные запросы. Он **не эксплуатирует**
уязвимости: не отправляет `WINDOW_UPDATE`-флуд, не рвёт потоки через
`RST_STREAM` и не пытается вызвать падение воркера.

## Уязвимости

| CVE | Что это | Уязвимы | Нужно для атаки |
|---|---|---|---|
| [CVE-2026-123007](https://www.cve.org/CVERecord?id=CVE-2026-123007) | переполнение окна flow control в HTTP/2 (RCE; major по NGINX, critical по Xint) | 1.9.5–1.31.8 | HTTP/2 |
| [CVE-2026-123634](https://www.cve.org/CVERecord?id=CVE-2026-123634) | use-after-free в resolver | 0.6.18–1.31.8 | `resolver` + `proxy_pass` с переменной + `mirror` |
| [CVE-2026-123633](https://www.cve.org/CVERecord?id=CVE-2026-123633) | use-after-free в HTTP/2 | 1.19.7–1.31.8 | HTTP/2 + проксирование на upstream |
| [CVE-2026-121810](https://www.cve.org/CVERecord?id=CVE-2026-121810) | use-after-free в HTTP/3 | 1.25.0–1.31.8 | HTTP/3 + проксирование на upstream |
| [CVE-2026-113425](https://www.cve.org/CVERecord?id=CVE-2026-113425) | use-after-free в mail proxy | 0.5.33–1.31.8 | `proxy on` + `auth_http` |

Официальные источники:
[nginx security advisories](https://nginx.org/en/security_advisories.html),
[nginx CHANGES 1.31.9](https://nginx.org/en/CHANGES),
[разбор Xint](https://xint.io/blog/nginx2root-remote-code-execution).

## Требования

- Python 3.8+ (проверено на 3.12), только стандартная библиотека.
- Для `--verify` нужен системный набор CA-сертификатов.
- Для интеграционных тестов — `docker` и `openssl`.

## Использование

```bash
./nginx2root_check.py https://example.com
./nginx2root_check.py example.com:8443 --timeout 8
./nginx2root_check.py https://example.com --json > report.json
./nginx2root_check.py --file targets.txt --concurrency 4
cat targets.txt | ./nginx2root_check.py --no-h3
```

Полезные флаги:

| Флаг | Смысл |
|---|---|
| `--json` | машиночитаемый отчёт (схема ниже) |
| `--port N` | переопределить порт для всех целей |
| `--path /x` | путь для fingerprint-запроса |
| `--timeout S` | таймаут соединения/чтения, по умолчанию 5 с |
| `--attempts N` | повторов при таймауте/сетевой ошибке (по умолчанию 3) |
| `--no-h2-request` | только ALPN, без HTTP/2-запроса |
| `--no-h3` | не проверять HTTP/3 (Alt-Svc и QUIC) |
| `--verify` | строгая проверка TLS-сертификата (по умолчанию выключена) |
| `--concurrency N` | параллельность в batch-режиме (по умолчанию 2) |
| `-v` | диагностика в stderr |

Коды выхода: `0` — проблем не найдено и непроверенных CVE нет, `1` — есть
`LIKELY_VULNERABLE`, `2` — результат неопределён (CDN, неизвестная версия,
нужна проверка на сервере, ошибка), `3` — ошибка аргументов.

## Что именно проверяется

1. **TLS/ALPN.** Отдельное рукопожатие с `ALPN=["h2","http/1.1"]`. Если сервер
   согласовал `h2`, значит HTTP/2 включён на этом порту — это условие
   CVE-2026-123007 и CVE-2026-123633.
2. **HTTP/1.1 fingerprint.** `HEAD /` и, если версия не видна, `GET` на
   несуществующий путь: `Server:`, тело дефолтной страницы ошибки, признак
   дистрибутивной сборки (`(Ubuntu)`, `(Debian)`), заголовки CDN. OpenResty,
   Tengine, Angie, Kong и APISIX распознаются как nginx-семейство: они
   содержат ядро nginx и подвержены тем же CVE.
3. **HTTP/2-обмен.** Preface + `SETTINGS` + один `HEADERS` (`GET /`).
   Подтверждает, что за ALPN действительно живой HTTP/2. Никаких управляющих
   кадров, влияющих на окна.
4. **HTTP/3.** Заголовок `Alt-Svc` с `h3` и UDP-проба QUIC: отправляется
   `Initial` с неподдерживаемой версией, сервер должен ответить
   Version Negotiation.
5. **Вердикты.** Версия сверяется с диапазонами: `1.9.5–1.31.8` и
   `1.30.0–1.30.6` уязвимы; `1.31.9+` и `1.30.7+` исправлены; `≤1.9.4` не
   затронуты.

## Как читать вывод

Каждый CVE получает две вещи: **verdict** (метку) и **действие** — что делать.

| Метка | Код | Действие |
|---|---|---|
| ВЕРОЯТНО УЯЗВИМ | `LIKELY_VULNERABLE` | обновить nginx до 1.31.9/1.30.7 |
| ИСПРАВЛЕНО | `PATCHED` | ничего не делать |
| ПУТЬ АТАКИ ЗАКРЫТ | `MITIGATED` | ничего не делать (обновить при возможности) |
| НЕ ЗАТРОНУТ | `NOT_AFFECTED` | ничего не делать |
| НЕ ПРИМЕНИМО | `NOT_APPLICABLE` | — (сервер не nginx) |
| НЕОПРЕДЕЛЁННО | `INCONCLUSIVE` | проверить вручную: CDN/бэкпорт/ошибка связи |
| ПРОВЕРИТЬ НА СЕРВЕРЕ | `UNKNOWN` | проверить конфигурацию на хосте |

Последняя строка отчёта — прямой ответ на вопрос «надо что-то делать?»:

| `ИТОГ` | Значение | Код выхода |
|---|---|---|
| `ТРЕБУЕТСЯ ДЕЙСТВИЕ` | есть `LIKELY_VULNERABLE` | 1 |
| `НУЖНА РУЧНАЯ ПРОВЕРКА` | есть `INCONCLUSIVE` | 2 |
| `НУЖНА ПРОВЕРКА НА СЕРВЕРЕ` | есть `UNKNOWN`, но нет `LIKELY_VULNERABLE`/`INCONCLUSIVE` | 2 |
| `ДЕЙСТВИЙ НЕ ТРЕБУЕТСЯ` | только `PATCHED`/`MITIGATED`/`NOT_AFFECTED`/`NOT_APPLICABLE` | 0 |
| `ПРОВЕРКА НЕ ВЫПОЛНЕНА` | нет DNS/соединения, CVE не проверялись | 2 |

Если проверка невозможна (DNS, таймаут, TLS), таблица CVE не выводится —
вместо неё причина и рекомендация. При `--no-h3` вердикт HTTP/3 становится
`ПРОВЕРИТЬ НА СЕРВЕРЕ`; если это единственная неопределённость, итоговый код — `2`.
Если UDP/443 не ответил, HTTP/3 тоже помечается `ПРОВЕРИТЬ НА СЕРВЕРЕ`:
молчание UDP может означать фильтр, а не отсутствие HTTP/3.

Таймауты и сетевые ошибки повторяются до `--attempts` раз (по умолчанию 3).
Если ответ получен не с первой попытки, в `note` появляется строка
«связь нестабильна: успешный ответ получен с попытки N из M».

Версия берётся не только из `nginx/1.30.7`, но и из вендорских токенов:
`nginx-reuseport/1.30.7`, `nginx-naxsi/1.24.0`, `nginx-extras/1.18.0`.
Для таких сборок добавляется `note` с исходным токеном.

Пример:

```
== https://example.com ==
  Проверка     ВЫПОЛНЕНА
  TLS      TLSv1.3; ALPN=h2
  HTTP/2   согласован, отвечает
  HTTP/3   не обнаружен
  Server   nginx/1.24.0 (Ubuntu)
  CDN      не обнаружен

  CVE-2026-123007  НЕОПРЕДЕЛЁННО        дистрибутивная сборка (Ubuntu): возможен бэкпорт; HTTP/2 включён  → проверить вручную
  CVE-2026-123634  ПРОВЕРИТЬ НА СЕРВЕРЕ  нужен resolver + proxy_pass с переменной + mirror  → проверить конфигурацию на сервере
  ...
  Сводка: НЕОПРЕДЕЛЁННО=3, ПРОВЕРИТЬ НА СЕРВЕРЕ=2
  ИТОГ: НУЖНА РУЧНАЯ ПРОВЕРКА — автоматический вердикт невозможен
  2 CVE проверяются только на сервере — см. docs/server-check.md
```

При ошибке DNS:

```
== https://bad-host.invalid ==
  Проверка     НЕ ВЫПОЛНЕНА
  Причина      не удалось разрешить имя (DNS): bad-host.invalid
  Что делать   проверить домен/DNS и повторить проверку

  CVE не проверялись: нет соединения с сервером.
  ИТОГ: ПРОВЕРКА НЕ ВЫПОЛНЕНА — выводов об уязвимости сделать нельзя.
```

## Ограничения

- **Версия — не приговор.** Ubuntu 22.04 (`1.18.0-6ubuntu14.22`), Debian,
  RHEL и другие дистрибутивы бэкпортируют исправления, не меняя `nginx -v`.
  Для таких сборок чекер выдаёт `INCONCLUSIVE` — сверяйтесь с
  [USN-8955-1](https://ubuntu.com/security/notices/USN-8955-1) и аналогичными
  advisory.
- **CDN.** Если перед nginx стоит Cloudflare/Akamai/Fastly, проверка видит
  только edge. Чекер это распознаёт и выдаёт `INCONCLUSIVE`; для точного
  результата запускайте его против origin.
- **CVE-2026-123634 и CVE-2026-113425** определяются только конфигурацией.
  Снаружи их проверить нельзя — нужен доступ на хост.
- **Скрытая версия.** При `server_tokens off` остаётся вывод «HTTP/2 включён,
  версия неизвестна»; это трактуется как риск, потому что исправленные
  релизы вышли только 18.11.2026. OpenResty и другие форки скрывают версию
  ядра nginx — их патч-статус проверяется на хосте (`openresty -v`).
- **Фильтрация по IP.** Если TCP-порт открыт, но TLS-рукопожатие и
  HTTP-запрос молчат, это обычно geo/anti-DDoS-фильтрация вашей сети, а не
  проблема сайта: проверьте доступность с другой точки (SSL Labs, внешний
  fetch) и запустите чекер из разрешённой сети.
- Проверка не является пентестом и не гарантирует отсутствие уязвимости.

## Что сделать на хосте

Подробная пошаговая инструкция под root (версия, модули, конфиг, ALPN,
действия, признаки эксплуатации) — в [docs/server-check.md](docs/server-check.md).

Кратко:

```bash
nginx -v                       # 1.9.5..1.31.8 => код уязвим
nginx -V 2>&1 | grep -- --with-http_v2_module
sudo nginx -T | grep -nE 'listen[[:space:]].*http2|^[[:space:]]*http2[[:space:]]+on'
```

Обновление: nginx **1.31.9** или **1.30.7**, затем перезапуск (reload не
заменяет исполняемый файл). Временная мера для двух HTTP/2-CVE — `http2 off;`
в затронутых `server`-блоках; для HTTP/3 — убрать `quic`-листeners и
`http3 off;`; для mail proxy — закрыть IMAP/POP3/SMTP от недоверенных сетей.

## Тесты

```bash
python3 -m unittest discover -s tests -v   # юнит + локальные TLS/UDP-серверы
bash tests/integration/run.sh              # реальный nginx 1.31.8/1.31.9 в Docker
```

Интеграционный сценарий проверяет четыре конфигурации: HTTP/2 на уязвимой
версии (`LIKELY_VULNERABLE`), HTTP/2 выключен (`MITIGATED`), HTTP/2 на
1.31.9 (`PATCHED`), HTTP/3 на уязвимой версии (`LIKELY_VULNERABLE`).

## Этика

Проверяйте только свои серверы или хосты, на проверку которых у вас есть
письменное разрешение. Чекер не выполняет атакующих действий, но сам факт
сканирования может нарушать правила площадки или законодательство.
